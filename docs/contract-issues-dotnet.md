# Form-rules contract: notes from the .NET implementation

Found while implementing `backend/src/Modules/MatterFlow.Configuration/Domain/Forms/Rules` against `contracts/form-rules.md` v1. None blocks conformance (all 76 vectors pass); each lists the behavior implemented. Please confirm or amend the contract so the TypeScript engine matches.

1. **JSON `null` as a rule.** `showWhen: null` / `requiredWhen: null` / `availableWhen: null` are not discussed. Implemented: treated as absent (matches a nullable DB column), not `SCHEMA_VIOLATION`. A non-object, non-null rule is `SCHEMA_VIOLATION`.
2. **Pattern semantics differ by engine.** `RegexOptions.ECMAScript` makes `\s`, `\w`, `\d` ASCII-only, whereas JavaScript `\s` also matches Unicode spaces (NBSP, U+FEFF, ...). `$` in .NET also matches before a trailing `\n` even with ECMAScript. Features such as lookbehind, named groups with `(?<n>)` differences and `\p{..}` (JS needs the `u` flag) may compile in one engine only. Implemented: .NET behavior with a 250 ms timeout; an uncompilable pattern or a timeout yields `PATTERN` (never throws). Recommend publish validation restrict patterns to a common subset and test both engines.
3. **URL regex whitespace.** `\s` in the URL rule is implemented as the explicit JavaScript whitespace set (not .NET `\s`, which adds U+0085) and anchored with `\z`, so both engines agree.
4. **`maxLength` count.** Counts UTF-16 code units (`string.Length`), as the contract says; surrogate pairs count 2.
5. **Number precision.** "Compared by exact numeric value" is implemented with IEEE double (same as JavaScript), not `decimal`. Integers above 2^53 or decimals needing more than 17 digits can compare equal in both engines but are not "exact". Values outside double range (for example `1e999`) are `INVALID_TYPE`. The typed index uses `decimal` and skips values outside its range.
6. **Reference ids.** `ASSET_REF`/`USER_REF` accept integers up to 2^53-1 (JavaScript safe-integer limit) so both engines agree; larger values are `INVALID_TYPE`. `3.0` is accepted, `1e0` as well (it is a JSON number with integral value).
7. **Date literal validity.** The contract requires a rule literal for DATE to be a `yyyy-MM-dd` string; implemented as a real calendar date, so `"2026-02-30"` is `LITERAL_TYPE_MISMATCH`.
8. **Multiple definition errors.** Only duplicate field keys are specified to short-circuit. Implemented: all other checks run and every distinct code is reported (including `CIRCULAR_DEPENDENCY` after rule errors on other fields). A field with a bad rule skips the remaining checks of that rule only.
9. **Self-reference vs. other checks.** Order for a leaf is: unknown field, non-input target, self reference, operator, literal, option. A self-reference to a heading is therefore `INVALID_REFERENCE_TARGET`.
10. **`section` on a heading.** A heading may belong to another heading (nested sections inherit hidden state); only self-reference or a non-heading target is `INVALID_SECTION`. Heading cycles are `CIRCULAR_DEPENDENCY`.
11. **Option-bearing field without options / non-option controls with options.** Not checked here (architecture 7.5 minimum-option rule is outside the vectors). `options` on a non-option control are ignored.
12. **Field-key shape.** Keys are not validated against `^[a-z][a-z0-9_]{0,63}$` for field definitions (there is no definition error code for it); rule `field` references are, via the schema (`SCHEMA_VIOLATION`).
13. **Unknown submitted keys are case-sensitive and checked in submission order of `values`**; error ordering is normalized (fieldKey, then code, ordinal) in the result, as the contract compares sets.
