# Form-rules contract: issues found by the TypeScript implementation

Found while implementing `frontend/projects/form-engine` (ticket #31). All 7 items are **resolved** (ticket #54); the decisions are in `contracts/form-rules.md` and locked by the shared vectors (152; the TypeScript evaluator reproduces all of them: 89 evaluation, 63 definition-invalid).

1. **No definition code for malformed keys or unknown controls. Resolved.** `INVALID_FIELD_KEY`, `INVALID_OPTION_KEY` and `UNKNOWN_CONTROL` were added to section 4 and to both `validateDefinition` implementations.
2. **`validation.min`/`max` type is not tied to the control. Resolved.** NUMBER bounds must be finite JSON numbers, DATE bounds real `yyyy-MM-dd` dates, `min <= max`; a mixed or invalid bound is the definition error `INVALID_VALIDATION` (so the evaluator never coerces or silently ignores). Bounds on other controls are ignored. TypeScript no longer skips mistyped bounds at evaluation time.
3. **`validation.pattern` has no engine-parity rule. Resolved.** Portable subset (section 3.1), `INVALID_PATTERN` at publish; `portable-pattern.ts` is the TypeScript checker and a pattern that passes it runs through `RegExp` unchanged.
4. **No pattern error message in the schema. Resolved.** `validation.patternMessage` (1..200 characters) was added to the schema and both implementations; `validationMessage` uses it for `PATTERN` and the code is unchanged.
5. **Copy deck gaps. Resolved.** `contracts/form-rules.messages.json` has a message for every field error code (with control and bound variants) and every definition error code; `messages.ts` mirrors it and `messages.spec.ts` fails if they differ. `docs/ux/ux-spec.md` 8.3 now lists the same wording, including REQUIRED for checkbox, choice, date and reference controls. The "Email" row stays for the system requestor-email field only: there is no EMAIL form control, so no form-rules code maps to it.
6. **Required CHECKBOX UX. Resolved.** The contract keeps "answered, not necessarily true". The caller applies a `false` default where the form wants a plain checkbox (section 3 item 7); a required checkbox without a default is intentionally unanswered until toggled, as the renderer already does. No contract change.
7. **Architecture 7.3 text vs contract. Resolved.** `docs/architecture.md` 7.3 now points at the contract files for the schema and states the final semantics (split `compare` operators, ASCII-insensitive text equality without ordering, double numbers, portable patterns).
