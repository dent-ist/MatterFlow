# Form rules contract: issues found by the TypeScript implementation

Found while implementing `frontend/projects/form-engine` (ticket #31). None blocks conformance: the TypeScript evaluator reproduces all 76 vectors (60 evaluation, 16 definition-invalid) and implements the documented behavior in each case below. These are gaps for the contract owner to decide.

1. **No definition code for malformed keys or unknown controls.** `form-rules.md` section 1 requires field keys `^[a-z][a-z0-9_]{0,63}$`, option keys `^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$` and a known control, but section 4 has no code for violating them (only rule `field` references are pattern-checked, via `SCHEMA_VIOLATION`). `validate-contracts.mjs` checks these only in its vector generator. TS does not report them; the .NET publish validator should, and a code (for example `INVALID_FIELD_KEY`) should be added.
2. **`validation.min`/`max` type is not tied to the control.** The schema allows `number | string` for both on every control, and section 3 says NUMBER/DATE bounds are "numbers or `yyyy-MM-dd` strings". A NUMBER with `max: "5"` or a DATE with `min: 3` is not definition-invalid. JavaScript would coerce in `<`; .NET would not. TS ignores a bound whose JSON type differs from the value's type. Needs a definition code (or an explicit "ignored" rule).
3. **`validation.pattern` has no engine-parity rule beyond "ECMAScript".** Unicode flag, lookbehind and `$` handling differ between V8 and .NET `RegexOptions.ECMAScript` (which also rejects some syntax V8 accepts). The regex-compiles check is listed as "not vectored". TS treats a pattern that does not compile as not enforced. A common subset should be specified.
4. **No pattern error message in the schema.** UX spec 5.x (designer) promises "optional pattern with a plain-language error message", but `$defs/validation` has `additionalProperties: false` and no `patternMessage`. The renderer currently shows "Enter <label> in the expected format."
5. **Copy deck gaps.** `ux-spec.md` 8.3 has no text for `INVALID_TYPE` (except URL), `OUT_OF_RANGE`, `TOO_LONG`, `PATTERN`, `OPTION_NOT_ALLOWED`, `UNKNOWN_FIELD`, and no REQUIRED wording for CHECKBOX or reference pickers (the renderer uses "Select <field>." for checkbox, choice, date and reference controls). It lists an "Email" message but the control catalog has no EMAIL control. `form-engine/src/lib/renderer/messages.ts` holds the proposed wording; the UX owner should confirm.
6. **Required CHECKBOX UX.** Section 2 says a required checkbox is satisfied by `false` and fails only when unanswered. A native checkbox cannot be "unanswered", so the renderer starts it unanswered (`null`) and a user must toggle it once to answer. The contract does not say whether a form-level default of `false` should be applied by the caller (section 3 item 7 suggests yes).
7. **Architecture 7.3 text vs contract.** `docs/architecture.md` 7.3 still shows the combined `compare` schema node and ordinal ordering on strings; `form-rules.md` section 6 documents the refinement but the architecture example was not updated.
