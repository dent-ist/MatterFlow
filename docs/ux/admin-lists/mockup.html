The question this answers

"Where do I change the choices of a dropdown?" Today the answer is one of twelve tabs on four pages (Labels: 4, Matter Lists: 3, Asset Types: Link Roles, plus Custom Fields for a different job). The page name tells a person nothing about which dropdown a tab feeds. This mockup puts every list of choices on one page, grouped by what the list belongs to (Matter, Task, Notes, Assets), and says on each list what it is used for and where people will see it.

Why master-detail, not twelve tabs

  • People start from the thing they want to change ("the priority wording"), not from the page. The left pane is a catalogue they can scan and search ("Find a list"); the right pane is the editor they already know (Order, Name, In Use, Status, row menu).
  • One nav entry. Tabs cannot hold 9 items under 4 groups at 1366; a 320 px list pane can, and scrolls inside itself.
  • Each row carries a one-line "used for"; the editor header repeats it with "Shown on" chips, so a rename or deactivate is made knowing where it shows.
  • Selection is in the address (/admin/lists/priorities), so a link to one list still works for support and bookmarks.

Custom Fields: recommendation

Keep Custom Fields as its own page (variant A) and link both ways. It does a different job: it creates new fields on Clients, Matters and Projects, with versions (Draft, Published), a full-page form designer and its own permission. Putting that editor into the same right pane would give the pane two unrelated shapes and make "Lists" mean two things.

Discovery is solved by wording and links: the Lists page ends with "Need a new field instead?", the search says the same when someone types "field", and the Custom Fields page opens with "Looking for the choices of a dropdown?". A dropdown inside a custom field keeps its own choices in the form designer; that stays where it is.

Variant B (switch above) puts an "Extra Fields" section at the foot of the same left pane. One entry fewer in the menu and one place to look, at the cost of mixing two jobs and two editor shapes. Owner decision.

Permissions and what a person sees

  • Each list is still gated by its own permission. The pane lists only the lists the person may manage; a group with none is not drawn.
  • The nav entry "Lists" shows when any list is permitted (the same rule as today's Labels entry). With one permitted list there is no left pane: the editor fills the page (try "Manages Priorities only").
  • With 2 to 4 permitted lists (try "Manages Matter Lists only") the pane is shown without the search box.
  • "Viewer, read only" is shown for completeness. Today there is no view-only right: Manage opens the page, so nobody reaches a list they cannot edit. Showing lists read-only would need a new permission (owner decision, section 3 of the README).
  • Custom Fields and Asset Types keep CustomField.Manage and AssetType.Manage; the cross-link card is hidden from a person without it.

Focus order and keys (no new or changed shortcuts, #420)

  • Tab order: skip link, nav, Find a list, the list catalogue (one Tab stop; Up and Down arrows move between lists and open each, Home and End go to the first and last: keys of one focused widget, D-44b), the "New ..." button, the grid (name buttons, row menu buttons), the pager, the "Need a new field instead?" link.
  • No key is bound to "Find a list" (a "/" key would be a new shortcut). Typing starts in the box after Tab.
  • Reordering keeps its keyboard path: row menu "Move Up" and "Move Down" (drag is the shortcut for the pointer only).
  • Dialogs: Esc and scrim close, Tab stays inside, focus returns to the button that opened it. Choosing a list moves no focus away from the catalogue; a live region says "Priorities, 4 items".
  • Screen readers: the catalogue is a listbox named "Lists"; each option is read as "Priorities, 4 active, Urgency of every task".
