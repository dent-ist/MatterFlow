## 7. Risks

### 7.1 Security of the SQL runner

The control is the database login (spec 7.2); the parser is defence in depth. What exists and what is new in this plan:

| Risk | State | Action |
|---|---|---|
| Admin SQL writes or reads denied tables | Login permissions, catalogue test, startup probe, direct-login schema tests exist | Keep. Add the `xp_cmdshell`, other database and role membership lines to the direct-login test if missing (H2) |
| Starter reports (new code that runs as seed) read a table that a later script denies | New | CI test runs every starter through the real login (H1) |
| Seeder runs SQL on startup | New | The seeder only writes definitions; the SQL is validated and runs only through the engine on a user's click; no starter is executed at startup |
| New built-in `:CURRENT_USER_CAN_ASSIGN_MANAGERS` is spoofed through the request | New | Built-in names are rejected in user input (existing rule); add a test |
| CSV injection | CSV is new | Formula prefix on text cells and headers (spec 12.3), tests (g) |
| Export bypasses row cap or filters | New | The export walks the same `ResultQuery` index as the grid; test that rows equal the grid |
| Error text leaks object names | Exists for run; new endpoints (views, list, metadata) | Only problem-details with codes; test |
| Parameter values in the audit trail readable by any `Audit.View` holder | Real, open | Neutral run audit (#808) |

### 7.2 Sensitive matters, performance, bundle

- **Sensitive matters (option A).** A run reads all matters, including sensitive ones, whenever `Features:SensitiveMatterAccess` is on or off, because the visibility functions are denied to the report login. Not a defect under option A; it must be stated in the release notes and on the assignment screens (#808). Starter reports for roles that are not trusted must not select sensitive fields.
- **Performance.** Memory: one result per person, 512 MB budget, 50,000 x 20 columns; the perf run of H3 must measure sort of 50,000 rows (target 150 ms), page (50 ms), CSV (3 s), save to the store (2 s). A runtime-columns record grid with 50 rows per page is cheap on the client. Heavy report SQL is bounded by 60 s, global cap 4, 30 runs per hour per person.
- **Bundle.** Initial bundle was about 607 kB at plan time, limit 700 kB (guard `initial-bundle.spec.ts`). New code is all lazy (`features/reports/**`, loaded by `loadComponent`); the nav item is data in `nav-items.ts` (eager, a few lines). The generated client is one 580 kB source file and must keep being imported only through `await import(...)` or as a type from eager files. Measure after WP-RA2 (first eager change) and after WP-RA5. No Monaco or CodeMirror.
- **Interaction with View as (#828).** Not built; see #842.

### 7.3 No report login on the owner's demo stack: how QA covers Run Preview and Run

Facts: `npm start` runs `db:report-login:now` (script `tools/db/provision-report-login.sql`, login `mf_reports`, connection string in `appsettings.Development.json`) and Run Preview works there. The owner's long-running demo stack was started without the login, so Preview returns SQL error 18456 (review-22). **Do not change that stack or its database.** The plan for QA:

1. **Backend integration tests** (Testcontainers, `ReportTestHarness` creates the login and the user in the role): every run, preview, rows, export and views path including permission variants. This is the main proof and needs no demo stack. Run in slices as the QA report describes (disk).
2. **A QA stack of its own** (separate database name and ports, started with `npm start` or `npm run start:user1` which provision the login): the Playwright e2e for the flows in section 9, using the seeded starters. The e2e must fail with a clear message ("report login not ready, see Administration > Reports > Settings") if the health tab is not "Ready", never skip silently.
3. **Mocked-API component and unit specs** for the browser parts (`HttpTestingController`; for e2e the fallback `page.route` fixtures of a result with all column types, a truncated result, a 410, a 409, a 429, a 503 "reports are off") so the screens are tested at both sizes even where no login exists.
4. **Health tab test**: with no login the Settings tab and Preview say "not configured" without a stack trace (exists in the admin specs; keep it green).
5. **Runbook check** (H4, H5): the corporate steps of runbook section 11 verified on a clean database once.
