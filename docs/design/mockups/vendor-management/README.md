# Vendor Management and People: clickable mockup

Mockup only, no issue yet, no app code changed. Open `index.html` in a browser (self-contained: tokens copied from `docs/ux/tokens.css`, a PrimeIcons woff2, no network, nothing saves). The **Mockup Guide** pill at the bottom left lists every screen and a "Who is looking" switch (vendor manager, Project Manager, read only, no vendor rights). `index.html#vendor-note` jumps straight to a screen; add `?chrome=0` to hide the guide. Sizes: 1366x768 and 1920x1080 only (D-82). No keyboard shortcut is added or changed (#420); Esc closing a dialog is the existing dialog behaviour (D-31).

Sample data is invented (firms, people, matters, `.example` addresses).

## Pattern choices and why

- **Vendor detail is a drawer, edit is a dialog.** Guidelines D-31 and D-33: a right drawer is for reading and detail, create and edit open in a form dialog; the list stays visible behind the drawer. Vendors are reference data (tens to low hundreds, no tasks, no activity feed), so a full record page like Matters would be heavier than the job. The Contacts tab in the drawer is where contacts and notes are edited, which keeps the Edit Vendor dialog flat: a dialog may not open another dialog, and the Contact Note dialog opens from the drawer instead. If the owner wants a full record page later, the drawer tabs become page tabs unchanged.
- **No Team or Vendors tab; a side column on Summary (owner change, v3).** Both change rarely, so the matter tab strip stays as today minus Team (Summary, Tasks, Projects, Assets, Productions, Notes, Activities). The Details card gives up 340 px at the right; at 1366x768 it still shows all 14 fields with no inner scroll (2 columns; at 1920 it shows 3 columns and has spare room). The column scrolls on its own only if both panels are open and full on a short window; with the 3-row cap at 768 px it does not.
- **Collapsible panels, designed for "mostly zero or one vendor".** No vendors = one line with + Add Vendor; one vendor = one row; large lists are capped with Show All. Collapsing is per visit (not stored); the collapsed state keeps the count chip and the Blacklisted chip so a warning is never hidden by collapsing.
- **Edit is a dialog with inline rows, applied on Save (not a panel edit mode).** A 340 px panel is too narrow for a combobox that shows badge, company and a title select, and the guidelines send edits to a dialog (D-31). Apply on Save, because several rows are added, retitled and removed at once, a wrong pick is undone by Cancel, a new Person and its team row are saved together, and the Blacklisted tick must be done before anything is linked. Immediate saving would create People records and links one keystroke at a time with no undo. Cost: one more click (Save Changes). A dirty Cancel asks the standard "You have unsaved changes" question (D-31).
- **Keyboard: only the standard combobox keys inside the control** (Arrow Up/Down move through options, Enter picks, Esc closes the list). Nothing is registered in `shortcut-registry.ts`, so #420 is untouched.
- **The existing Team tab would be replaced** (matter-tabs.ts, D-44y and the matter-fields spec section 4 would be amended; `Team (n)` leaves the strip). Add/Edit Team Member (576 px dialog with "Fill from a User") is replaced by the inline rows.
- **What the Summary panel cannot show that the Team tab shows today:** Email and Company (only in Show All and in the Edit dialog, not in the panel row), the sortable, resizable record grid with 25/50/100 paging and the Columns chooser, the per-row Edit (name button) and Remove (now only in the Edit dialog), and the count in the tab strip (now a chip in the panel header). Rows beyond the cap are one click away. Team is no longer a deep link target (`?tab=team`). The separate multi-pick vendor dialog with Service, Area and Category filters is gone: the vendor combobox searches name, website and services only (see question 2).
- **People is its own main nav page**, because Project Managers maintain it as they work, not an administrator. Alternative: under Administration.
- **Services and Areas are shown as toggle chips** in the form (eight and six values). They should be admin-maintained lists: a new group "Vendors" in Administration > Lists (like Team Titles).
- **Colour and wording**: Preferred is the healthy tint with a verified icon, Blacklisted the red tint with a ban icon, never colour alone (word and icon always). Title Case for buttons, tabs, headings; sentence case for help text; dates MM/DD/YYYY; "(required)" on required labels (D-20, D-35).

## Proposed permissions (names follow `contracts/permissions.json`: `Noun.Verb`, group, description)

| Code | Group | Description | Proposed default |
| --- | --- | --- | --- |
| `Vendor.View` | Vendors | See the Vendors page, vendor details, and the Vendors panel on the matter Summary tab | Director, Project Manager, Pod Lead, System Admin |
| `Vendor.Manage` | Vendors | Create, edit and delete vendors; add and edit contacts and contact notes; maintain the Services and Areas lists | Director, System Admin |
| `Vendor.Link` | Vendors | Link and unlink vendors on a matter. Needs `Vendor.View` and `Matter.View` | Director, Project Manager, System Admin |
| `People.View` | People | See the People page. Pickers work for anyone who may edit a team or a vendor contact | Director, Project Manager, Pod Lead, SME Intake Coordinator, System Admin |
| `People.Manage` | People | Create, edit and delete people, including the quick "Add New Person" in pickers | Director, Project Manager, System Admin |

Rules: the role editor selects `Vendor.View` when `Vendor.Manage` or `Vendor.Link` is ticked (same as the Dashboard tabs). `Matter.Edit` stays what gates Edit on the Team panel (D-44y). Seeding the defaults would be one numbered script in `db/scripts/` plus `Permissions.cs` and `permissions.ts` in step; nothing is deployed, so no backfill.

## Open design questions for the owner (most important first)

1. **Apply on Save or immediately?** The mockup applies the Edit dialog's changes on Save (reasons above). Confirm, or say you want each pick saved at once.
2. **Vendor filters.** The old picker had Service, Area and Category filters; the combobox has search only. Is name, website and service search enough for the vendor list size, or should the dropdown carry filter chips?
3. **Are system users automatically in People?** Recommendation: yes. Every user appears as a System User row, read only for name and email (maintained on Users), so nobody types a colleague twice. "Internal" without a login (a partner who never opens MatterFlow) is still possible and editable. If you want People to be only typed-in contacts, the Team picker loses "pick a user".
4. **One flag per contact or a history?** The mockup keeps one current flag with date, reporter and note (what you described); the earlier text is in the audit trail. A contact flagged Do Not Hire and later cleared would otherwise need a log of notes.
5. **What happens when someone links a Blacklisted vendor?** Mockup: allowed, with a warning and an "I have read this" tick. Alternatives: hard block, or allowed only with a new permission such as `Vendor.LinkBlacklisted`. Recommendation: the tick (shown), because the firm may legitimately keep a vendor on an old matter.
6. **Category has only Preferred and Blacklisted.** A vendor that is neither vetted nor bad has to pick one. Recommendation: add a third value "Approved" (no icon) or leave Preferred as the default. Your call.
7. **Delete rule.** Mockup: a vendor linked to any matter cannot be deleted (dialog explains, suggests Blacklisted); an unused one can. Other lists in the app deactivate rather than delete when in use. Do you want Deactivate instead?
8. **Title or Role versus Title on This Matter.** A person has one free-text Title or Role (Partner); the Team panel keeps its separate "Title on This Matter" from the Team Titles list (Opposing Counsel). Recommendation: keep both. Say if you want to drop one.
9. **Who may create a person from the Edit Team row?** Recommendation: `People.Manage`, given to Project Managers by default. Without it the Create option is shown disabled with the reason.
10. **Hidden or disabled?** Whole pages and tabs are hidden when the person has no right (the app's rule). The Vendors panel Edit button is shown disabled with the reason, because that is the one thing a Project Manager comes to the box to do and should know whom to ask. Is that exception acceptable?
11. **Visible rows.** Cap 3 at 768 px high and 5 at 1080 (the side column has room for about 3 rows per panel at 768). Right number?
12. **Should Do Not Hire flags also warn in the matter Team panel** when the same person is on a team (they could be a vendor contact and a team member)? Not built.
13. **Link extras.** Today a link is only vendor + matter + who + when. A "role on this matter" or a note per link (for example "Review vendor, wave 2") would be a small add. Not built.
14. **Existing team entries.** Typed-in team members on matters would need to become People. The app is not deployed, so the mockup assumes no migration; confirm.
15. **People in the main nav or in Administration?** Mockup: main nav, right under Vendors.

## Rough build estimate (not a commitment)

Frontend about 28 to 38 agent-hours (Vendors grid, drawer, forms, picker dialog, Summary Team and Vendors paneles, People page and dialogs, person picker reused in Team and vendor contacts, nswag client, specs, e2e). Backend about 14 to 20 hours (Vendors, VendorContacts, VendorMatters, People tables via numbered scripts; a People module or part of Identity; Team table gets a PersonId; endpoints, permissions, audit events, OpenAPI sync). Risks: the Team change is the only one touching existing behaviour; module boundaries (a People and a Vendors module may only share `.Contracts`); Details card height at 1366x768.
