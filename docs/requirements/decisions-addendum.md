# Decisions Addendum to Requirements Baseline v1.1

**This addendum OVERRIDES `baseline-v1.1.md` wherever they conflict.** It records decisions made with the product owner after the baseline was written (2026-10-14). Read the baseline first, then this file.

## A. Task immutability and editing

- A Task's **Task Type, Workflow, and Matter cannot change** after creation. Recovery from a wrong entry is Cancel and recreate.
- A Task's **Project may change**, within the same Matter.
- Task form values (Task Type request form) are **editable** and audited. Values stay on the form version the Task was created under.
- Editing a **Completed or Cancelled** Task requires first moving it back to **In Progress** (both are reopenable; Cancelled is not terminal). Reopening is blocked while the Matter is inactive.
- A Task can be **Cancelled from any open state** (New, In Progress, On Hold), with a **mandatory comment** (PM decision, Task Queue review BUG-TQ4: a Completed or Cancelled task is only reopened); unresolved workflow steps do not block Cancel.
- Reopening a step on a Completed Task **auto-moves the Task to In Progress** (audit both events).
- **Assigning a user** moves a New Task to In Progress automatically. Pod-only assignment does not. Unassigning later does not revert status.
- Editing a Step Definition in the library **does not** change already-published Workflow Versions (snapshot on publish).

## B. Matters and Clients

- Tasks can be created only on an **active** Matter.
- A Matter can be set **inactive only when all its Tasks are Completed or Cancelled**.
- **Client and Matter numbers** are 1 to 5 digits as entered (e.g. `343`), never more than 5. The system **normalizes to a zero-padded 5-character string** (`00343`) and stores/enforces uniqueness on that. Search and lookup accept padded or unpadded input. Combined display is `00343-00012`. This replaces the baseline's "exactly five digits as typed" rule.
- An **inactive Client cannot get new Matters** (the server refuses with `CLIENT_INACTIVE`; the UI disables New matter with the reason). See section V.

## C. Requestor, attachments, intake

- Task has **Requestor Name (required)** and **Requestor Email (optional)**. Requestors are not app users (attorneys/paralegals are not users in this phase). Email "From" prefills these.
- **The system stores no attachments and no original email files.** Removed: `TaskAttachment`, the File Upload form control, source-email preservation, OPEN-10 (storage/scanning/retention). Outlook intake is **parse and discard**: extract Subject, Body, From (name/email), and sent date. Attachment filenames are not recorded.
- Firm uses **new Outlook**. Drag-and-drop feasibility from new Outlook into a browser is an unvalidated technical spike. Design intake so a paste / manual-entry path always works; drag-drop is an enhancement.

## D. Comments

- Rich text, **basic formatting only** (bold, italic, lists, links), sanitized server-side. No attachments. **Internal only.**
- Delete is **soft-delete**: hidden from the UI, retained in the database for audit. Authors may edit/delete their own comments; edit history kept. (Assumed; low risk.)

## E. Security and identity

- **Phase 1 visibility: anyone with `Task.View` sees all Tasks.** System Admin has full access. **Ethical walls and Matter-level ACLs are deferred to a later phase.** Read-access logging is out of scope.
- **Pod Lead is a role** (permission set), not a per-Pod flag.
- Offboarding is manual (admin reassigns Tasks one by one). Task Queue assignee filter includes inactive users.

## F. Scope reductions and removals

- **Dropped:** global Task custom fields (only per-Task-Type forms remain). Subtasks, dependencies, related-task links, cloning/templates. Bulk "reassign all". Reports/exports (dashboard only). Read-audit logging.
- Custom fields remain for Client, Matter, Project, Asset. Admins define Asset Types with their own fields. An Asset belongs to exactly one Matter. (Asset-Type-specific fields may be modeled as the Asset Type's form.)

## G. Dates and sorting

- **Due Date is optional; its time part is optional.** No due date = **ASAP** (never overdue). Date-only due date is overdue after 23:59 **firm time** on that date; with a time, overdue after that time. **One firm timezone** applies to all users; store UTC.
- **ASAP sorts above explicit due dates** within a priority.

## H. Scale (drives architecture)

- 200 to 300 users; 10+ new Tasks/day (a few thousand/year); 200 to 300 Assets per Matter. **Small scale: modular monolith, SQL Server only, plain indexes; no search engine, no full-text required.**

## I. Build assumptions for engineering

- Backend: ASP.NET Core (current LTS), EF Core, SQL Server. Frontend: Angular (current stable) with a mainstream component library chosen in the architecture doc. Same-origin deployment preferred.
- Auth: Windows Integrated Authentication with JIT zero-permission user provisioning (baseline §6.4). In dev/test, a switchable **development auth provider** is acceptable so the app is runnable off-domain.
- Initial System Admin is seeded via configuration.

## J. Database migrations (decided 2026-10-14)

- The schema is managed by **hand-written, numbered SQL scripts** (`01-init.sql`, `02-new-table.sql`, `03-....sql`, ...), **not EF Core migrations**. EF Core is used for data access only; no `Add-Migration`.
- A small **migration table** (e.g. `dbo.SchemaMigration`: script name, numeric prefix, checksum, applied-at UTC, duration, success) records each executed script.
- **On server startup**, the app discovers `.sql` files (embedded resources or a configured folder), compares them with the table, and executes the pending ones **in numeric-prefix order**, each in a transaction where SQL Server allows. Already-applied scripts are never re-run.
- Safeguards: a SQL Server **application lock** (`sp_getapplock`) so multiple instances don't migrate concurrently; **fail startup** on any script error; detect **duplicate prefixes** and **checksum changes of already-applied scripts** (fail loudly); support GO batch separators.
- Developers add scripts only by appending new files; applied scripts are immutable.

## K. Completing a Task with unresolved steps (decided 2026-10-14)

- The user can click **Complete** on a Task even when workflow steps are unresolved. The app shows a confirmation: *"You have N steps not completed. Do you want to mark them all completed?"*
- **Confirm** marks all unresolved steps **Completed** (in workflow order for ordered workflows) and then completes the Task, in **one transaction**. **Cancel** leaves everything unchanged.
- This is **Completed, not Skipped**. Skip stays a per-step action (with the comment rule where configured).
- **Guard:** a step whose **required inputs are missing** cannot be auto-completed. The dialog lists those steps and the Task stays open until the user fills them in (the user may skip any that are skippable). Only steps with all required inputs satisfied are bulk-completed.
- Audit: each step completion is recorded individually, sharing one correlation id with the Task completion, flagged as "bulk completed".
- This supersedes the earlier "every step must be individually resolved before the Task can be completed" assumption (baseline 9.4/9.5, architecture OPEN-05).

## L. Admin account, timezone, AD lookup (decided 2026-10-14)

- **Initial System Admin:** `ke\kekim` (`Bootstrap:SystemAdmins`, domain `KE`, SAM `kekim`; match case-insensitively).
- **Firm timezone: Eastern** (`America/New_York`, Windows id `Eastern Standard Time`; DST-aware). Technicians work across all US timezones. **Due dates and times are entered, displayed and judged for overdue in Eastern Time and always labeled "ET"** regardless of where the user is. Date-only due dates are overdue after 23:59 ET. Timestamps stored in UTC. (Per-user display timezone is a possible later enhancement.)
- **AD profile lookup (display name, email):** permitted **only if it needs no separate access that IT must provision.** Windows authentication itself supplies only the account identity, not name or email, so a lookup is a separate directory read. Design: optional and **off by default** (`ActiveDirectory:LookupEnabled`), reading with the web app's own identity; on any failure fall back to showing `KE\sam` and let an admin edit the display name and email. Whether the production server's identity can read AD is to be confirmed with IT at deployment; the app must work fully without it.

## M. Local-time display, including due dates (decided 2026-10-14)

**Supersedes the "ET-only" parts of sections G and L.** The product owner prefers each user's **local time** everywhere; technicians work across all US timezones.

- The browser sends its IANA timezone with each request (e.g. `X-Time-Zone: America/Chicago`); the server falls back to `America/New_York` (the firm default, `Firm:TimeZoneId`) if absent or invalid. Timestamps are stored in UTC.
- **Comments, activity/audit and all other timestamps** display in the viewer's local time with the zone abbreviation. (The Due cell of the work grids is the one exception: it shows no zone abbreviation in the cell and keeps it in the tooltip, section U.)
- **Due date with a time** is an absolute instant (`DueAtUtc`). The creator enters it in their local zone; every viewer sees it converted to their local zone. Overdue when now is past that instant (same answer for everyone).
- **Date-only due date** is a floating calendar date (no zone). It is overdue after 23:59:59 on that date **in the viewer's local zone**, so two viewers near midnight may disagree. Accepted trade-off.
- No due date = ASAP, never overdue; ASAP still sorts above explicit due dates within a priority.
- Overdue filters, dashboard counts and queue sorting use the **requesting user's** timezone. For sorting, a stored `DueSortKey` (the instant, or the date at 23:59:59 treated as UTC) gives an approximate order; the exact overdue flag is computed at query time. At this scale (a few thousand Tasks a year) query-time evaluation is acceptable.
- Schema effect: replace `DueTime` + `OverdueAfterUtc` with `DueDate date NULL`, `DueAtUtc datetime2 NULL` (set only when a time is chosen; CHECK it implies `DueDate`), and `DueSortKey datetime2 NULL`.

## Q. Task type coverage: completion counts per person for training (decided 2026-10-15, issue #73)

- The product owner asked for a view of **how many tasks each person completed per task type in a period**, to see who is not handling certain types of work and needs training or cross-coverage.
- This **supersedes the "no completion statistics, no per-person performance metrics" note of the Dashboard epic (#68) for this one view only.** The Swimlane and Users workload views stay operational-capacity views with no completion counts, speed or ranking.
- It is a **Coverage view inside the Dashboard Users tab** (`?tab=users&view=coverage`), headed "Task type coverage - use this to plan training and cross-coverage, not to rank people". There is no ranking, score or "best / worst" wording; ordering by total is allowed and labelled neutrally ("By total completed"). Zero cells are shown as possible training gaps, and the view counts how many people handled each task type (fewer than two is flagged: a bus-factor insight). *Amended by the UX review 2 paragraph at the end of this section (C1, C2, C3): the default orientation, the gap toggle and the two statements.*
- **Read access is limited by its own permission, `Dashboard.ViewCoverage`** (separate from the Users tab permission), granted to Director and Pod Lead by default. The endpoint is `GET /api/v1/dashboard/coverage`.
- **What counts:** tasks with status COMPLETED (not cancelled) whose completion time falls inside the period in the viewer's time zone, counted for the person the task is **assigned to** (the Task keeps no separate "completed by", and a completed task cannot be reassigned, so this is the person who held it when it was completed). Inactive users appear only when they completed something in the period (marked Inactive). Availability is shown as a small marker only and never changes the counts.
- **Audit:** reading the view writes nothing extra to the audit log.
- **Amendment (UX review 2, WP11, issues #134, #135, #136; decided by the PM 2026-10-16).**
  - *Orientation (C1).* The default of Coverage is **"By task type"**: one row per task type with the names of everyone who completed at least one task of it in the period (first five, then "+N"), the number of people, the tasks completed and a status. Names inside a row are always alphabetical, never by count, so nothing ranks people; rows are ordered "Fewest people first" (default, ties by name), "Type name" or "Most completed". The person-by-type **matrix stays as the second option** (`cov=matrix` in the address only when chosen). The counts per person appear only in the row's details and each opens the tasks behind it. "Who has NOT handled it" is a control limited to the scope's pod ("Show people in <pod> who have not handled this type"; with all pods it asks to pick a pod); it lists names with a neutral 0. The endpoint takes `groupBy=type` (additive); the counting rules above are unchanged, so the counts equal the matrix and the Completed figure of the period.
  - *Zeros (C2).* This **amends "zero cells are shown as possible training gaps"**: zero cells of the matrix are blank (named "Ana B., Redaction: 0 completed" for screen readers and in the tooltip), and the possible training gaps are outlined with an icon **only while the "Training gaps" toggle is on** (default off), because the By task type view is now the planning surface.
  - *Wording (C3).* This **amends "fewer than two is flagged"**: **zero is informational, exactly one is the warning.** Two statements replace the single banner: neutral and collapsed "N task types had no completed tasks in this period." (with the hint to try a longer period) and, only when above zero, amber with an icon in a `role="status"` region "N task types were handled by only one person in this period: <type names>. Consider cross-training." The status column says "No one" (neutral) and "One person" (amber). The words "gap" and "bus factor" are not used in the statements, the status or the summary (the matrix toggle keeps its name, "Training gaps").

## R. Rich-text Task description with safe tables (decided 2026-10-15, issue #80)

Technicians paste long email instructions, often with tables, into the Task description. This **relaxes addendum D** ("basic formatting only") **for tables only**, in the Task Description and in comments.

- **The Task Description is rich text**: the formatting of comments (bold, italic, bulleted and numbered lists, links) **plus tables**. Comments accept tables too. Nothing else is added: no images, colours, fonts, styles, classes, scripts, forms or embedded content.
- **Server-side allow-list (authoritative; one sanitizer for comments, descriptions and email intake).** Tags `p br strong b em i u ul ol li a table thead tbody tfoot tr th td caption colgroup col`. Attributes: `href` on `a` (same link rules as before: `http`, `https`, `mailto`, absolute, no credentials, no direction controls, no markup characters), `colspan` and `rowspan` on cells (plain integers 2-100; 1 is dropped), `scope` on `th` (`row`, `col`, `rowgroup`, `colgroup`). **No** `style`, `class`, `id`, `width`, `bgcolor`, event handlers, `img`, `svg`, `math`, `iframe`, `form`, `style` or `script`.
- **Limits.** Nested tables to depth 3 (deeper tables are flattened into paragraphs). At most **200 table cells per field**. A description: at most 100,000 characters of stored HTML (`HTML_TOO_LARGE`), 20,000 visible characters (`TOO_LONG`, as before), 300,000 characters accepted before sanitizing, and a limit on tags and nesting (`TOO_COMPLEX`). Cells over the limit: `TABLE_TOO_LARGE`. A comment: 20,000 characters as before, same table limit. Errors are field errors with a clear message, never a silent cut.
- **Storage.** `dbo.Task.Description` stays `nvarchar(max)`; new column `DescriptionFormat` (`TEXT` | `HTML`, script 26). Existing descriptions stay `TEXT` and are shown escaped with their line breaks until the description is edited; new and edited descriptions are `HTML` (the sanitized form is what is stored and returned). A client that sends an unchanged text description back (a title edit, an older client) does not convert it and creates no audit entry. Plain text sent to the API is escaped into paragraphs.
- **Plain-text uses.** The audit trail, the swimlane summary and any list snippet or export use a plain-text rendering of the description (paragraphs and table rows on lines, cells separated by " | "); the audit never stores markup.
- **Editor.** The Create Task form and the Edit dialog use the rich text editor with table support: Insert table (up to 8 x 8, optional header row), add and delete rows and columns, Tab and Shift+Tab between cells (Tab never traps the keyboard). Pasted or dropped HTML (Outlook, Word, web pages) is rebuilt from the same allow-list before it is inserted; a table over 200 cells is pasted as text. The read view shows the table in its own scrolling box.
- **Email intake** (parse and discard, unchanged in principle): the sanitized HTML body (`.eml`, `.msg`, and the clipboard HTML of a pasted email) becomes the description with its tables; the plain-text body is the fallback when the HTML is over a limit. The **privilege reminder** stays on intake, the Task Description and comments.
- **Defence in depth.** The browser renders stored HTML through Angular's own sanitizer as well, and drops images, frames and forms again; the sanitizer's output is verified to be a fixpoint on every save; the security tests (hostile corpus, fuzz, round trip) and the residual risks are in `docs/qa/security-review-2-resolutions.md`, "Addendum 3".

## U. Task Queue and shared grid decisions (decided 2026-10-18, epic #195; documented in issue #239)

Decided by the PM on the owner's approval of the Task Queue review ("create epic and issues from the Task Queue review"; product decisions delegated to the PM). The behaviour is specified in `docs/ux/ux-spec.md` 4.6 (Due cell), 5.2 (grid contract), S03 and S04; the numbers are in `docs/ux/tokens.css`; the plan and the evidence are in `docs/ux/task-queue-review/`. The shared grid serves the Task Queue, My Work, Pod Work and the Matter and Project task lists, so every rule below applies to all of them.

- **Zone abbreviation dropped from the grid Due cell.** The Due cell (and the Dashboard lists, Swimlane card and task header that use it) shows no zone abbreviation. A timed due keeps it in the cell tooltip ("Oct 17, 2026, 6:00 AM EDT"). Section M is kept in full for every other timestamp (comments, activity, task detail); only the display of the Due cell changes.
- **Due text.** Eight states (ASAP, overdue with a time, overdue with a date only, due today, tomorrow, in 2 days, later, closed); "In 2 days", not "Due soon"; no "Overdue 9w" cap (hours, then days); the year only outside the current year in the viewer's zone. One spoken sentence per cell, line 1 is a `<time>`.
- **Closed tasks only reopen (BUG-TQ4, #235).** Amends section A: a Completed or Cancelled task is never cancelled or completed directly. - **Names of the tabs (#261, #263, #257, #248).** The first tab of a Client and of a Matter is **Overview** (the key and the address are unchanged: no `tab` in the address, and `?tab=details` still works). A Project has two tabs, **Tasks (n)** first and **Details** second (`?tab=details`). The browser title uses the visible tab label without its count (`00107 Hartwell & Bryce LLP: Matters - MatterFlow`), the record text cut at 60 characters in the title only.
- **One record header (#253, #254, #256).** The header of a Client, Matter or Project is the same component. Breadcrumb: the last step is the current page, cut at 40 characters with the full text as a tooltip and for screen readers (the review's alternative, dropping the last crumb, is rejected). Title: the number or reference and the name on one line at the H2 size (22 px; 18 px on a phone), the name clamped to two lines with the full text as a tooltip. A muted context line names the parent (`Client ...` on a Matter, `Matter ...` on a Project) and links to it only with the parent's View permission. A Sensitive matter has a one-line note under the title (a warning only, as in section F). Below 640 px the crumb becomes a "Back to Matters" link that shares a row with the primary action and the overflow.
- **Header action rule (#255, reverses a review proposal).** The header holds, in this order, **Edit, Activity, the primary create action** and a "..." overflow menu. Client: New matter; overflow Set inactive / Set active. Matter: **Create task**; overflow New project, New asset, Set inactive / Set active. Project: Create task; overflow Archive / Restore. Nothing that changes a record stays in a tab body; the empty states of the Projects and Assets tabs keep their own creation button. **This reverses the review's proposal "New project in the header":** three create buttons do not fit at 768 px, so only the primary action is a button and the other creations live in the overflow. On a tablet (640 to 1023 px) the primary action and one of Edit and Activity stay as buttons, on a phone only the primary action; whatever does not fit moves to the overflow in the order Edit, Activity, creations, state change. A person with only View permissions sees no action buttons and no "..." menu. Labels: **"New X" for records, "Create task" for tasks, never a leading "+" in the label** (#250); the icon is decoration.
- **The summary strip (#260, #261, #263, #264).** Five items in one fixed order, the Dashboard's: **Open, Overdue, Due soon, ASAP, On hold** (the review proposed four counts; Due soon is added so the strip speaks the Task Queue's vocabulary). On the Client and Matter Overview the items are links: a Client's go to the Task Queue scoped by `client=`, a Matter's to the matter's own Tasks tab (`?tab=tasks&view=overdue|dueSoon|asap|onHold`; Open is `?tab=tasks`). Above the Matter and Project Tasks grids the same strip is a set of toggles (Open is the grid's default and shows pressed when no `view` is set). A zero is muted, Overdue keeps red with an icon and the word, an unknown number is `--`. Without `Task.View` there is no strip and no number.
- **Counts: definitions (#258, #259).** The words are those of the Dashboard and the Task Queue (sections T and U): Open = New, In Progress or On Hold; Overdue = open and past its due moment in the viewer's zone (a date-only due floats; ASAP is never overdue); ASAP = open without a due date; On hold = status On Hold; Due soon = open, not overdue, not ASAP, due today up to today plus 2 days (the Dashboard tile). A client's count covers all its matters, a matter's includes its project tasks, a project's its own; inactive matters and archived projects count. The strip number, the count in a list and the total behind each link are the same number (integration and e2e tests assert it in three time zones).
- **Counts API shape (#258, #259), additive.** `openTaskCount` and `overdueTaskCount` on the client, matter and project responses (lists, Get and the create/update replies); `clientNumber` and `clientName` on the project response; sort keys `openTasks` and `overdue` on the three list endpoints; and `GET /clients|matters|projects/{id}/summary`. **A count is `null` without `Task.View`: never a 403 and never a fake 0**, so the UI leaves the strip and the two count columns out instead of drawing zeros. The summary's `topMatters` (a client only) holds at most 5 matters that have open tasks. Details and the exact fields are in `docs/architecture.md` section 11. No SQL script was needed (script 28 stays free); the OpenAPI file and the TypeScript client are regenerated after every rebase, never merged by hand. **Code versus issue:** the issue said `topMatters` omits matters the viewer cannot see; the code returns `null` for the whole list without `Matter.View` (there is no per-matter visibility rule in the API, so nothing else can be omitted).

- **Project Details drops the side panel (#257).** The Project page has the same tab strip as the other records and uses the full width; the shared two-column layout (`mf-detail-layout`, `mf.detail-panel.open`) stays for the Task page only and the stored panel preference is ignored on a Project. 10. **Bundle (owner):** Reports pages are lazy routes; the generated api-client and lookup-store are never imported statically from eager shell code; initial bundle stays under 700 kB.

## AL. Admin impersonation, "View as", read-only (decided 2026-10-26 by the owner, epic #828, phase-22; design `docs/ux/impersonation/README.md`, plan `docs/ux/impersonation/delivery-plan.md`)

**Status (2026-10-26): planned; not started** (the owner asked for design, plan and epic only). Priority: higher than the postponed Reports epic #671.

1. **Read-only.** While an administrator views as another user, every write is refused by the server with HTTP 403, `application/problem+json`, stable code `IMPERSONATION_READ_ONLY` and a short message. Allowed: GETs, stopping the impersonation and normal sign-out. Nothing may change data, mark the target's notifications read, move the target's "Since your last visit" marker or change their saved scope/menu preferences (preferences are read from the target; writes are refused or ignored).
2. **Who can be impersonated.** Any active user except System Administrators (never, not even by another System Administrator). An access-pending user and a disabled user cannot be.
3. **Duration.** At most one hour (fixed, not sliding), then it ends by itself and the next request behaves as the admin again, with a notice. The admin can stop at any time. Starting a new one replaces the previous one.
4. **Permission.** New `User.Impersonate`, held by default only by the System Administrator role (implicitly, no grant row), assignable to any other role. The Roles screen warns that holders see the application as any non-administrator, including sensitive matters.
5. **Transport.** Works with the Dev provider and Windows authentication. The real principal is never replaced: the server resolves an effective user from an opaque, revocable, server-side session (cookie `mf_view_as`, HttpOnly, SameSite=Strict, only a SHA-256 hash stored), bound to the real user, checked on every request, valid on every node. The effective user drives authorization, data scoping and "my" views; the real user is kept for audit.
6. **Audit.** Start, stop and expiry are audited events (who, as whom, when, from where). `ActorUserId` is always the real user; a new column carries the effective user, so audit views read "by <admin> (as <user>)". Refused writes are logged at a low level and rate-limited; they are not an audit flood.
7. **Screens.** "View as..." in the account menu (permission only), a searchable picker (ineligible users listed with the reason), a persistent banner on every page including phone and error pages ("Viewing as <name> (read-only) * expires in 58 min * Stop"), a live-region announcement on start, stop and expiry, write buttons visible but disabled with "Read-only while viewing as someone else". No new or changed keyboard shortcuts (#420); the initial bundle stays under 700 kB (picker and banner logic lazy).
8. **Safety net.** Default-deny middleware for every non-GET, a data guard, and an endpoint catalog with a coverage test (same approach as sensitive matters) so a new write endpoint cannot bypass the rule. GETs that wrote (the first read of My Matters activity creates a marker row) are fixed.
9. **No SQL script number is claimed:** next free number at implementation time; a new table needs `db/report-access.json` and GRANT/DENY for `mf_report_reader`.
10. **Open questions** Q1 to Q6 in the design (non-admin holders, telling the target, Reports, a reason text, several tabs, downloads), each with a recommended answer; none blocks the start.
